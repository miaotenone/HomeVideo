# HomeVideo 家庭边缘监控技术方案

文档状态：设计方案，等待实机验证  
设计日期：2026-10-13

## 1. 项目目标与约束

利用现有闲置设备实现家庭远程监控，优先让 V831 承担视频处理和智能检测，减少树莓派的持续计算负载。

### 1.1 现有设备

| 设备 | 本项目中的安排 |
| --- | --- |
| Sipeed Maix-II Dock，V831 | 主摄像头设备，承担采集、编码、检测和事件录像 |
| 树莓派 4B，8GB | 远程访问、报警通知、事件归档和回溯 |
| K210、ESP32-CAM | 保留作为后续实验或扩展设备 |
| K230 | 用户已有实验用途，首版不依赖 |

### 1.2 已确认需求

- 手机在外网查看实时画面。
- 离家布防期间检测人员入侵。
- 持续检测可见的疑似火焰和烟雾，触发报警。
- 保存事件截图和前后录像，支持手机回溯。
- 日常视频不长期保存。
- V831 尽量独立完成监控计算，树莓派不常驻运行视频识别。

后续扩展包括人脸身份识别、其他物体检测及更多机位。远程断电设备及控制逻辑不属于本方案范围。

首版按一路摄像头、一个实时观看客户端设计。本文中的初始参数、软件候选和验收目标属于设计建议，均需通过实机测量确认。

## 2. 已知能力与待验证项

[Sipeed 官方硬件资料](https://wiki.sipeed.com/hardware/zh/maixII/M2/resources.html)说明，V831 具备：

- H.264/H.265 硬件编码能力，官方标称最高 1080p、30fps。
- 64MB 内存。
- 约 0.2 TOPS 的 AI 加速能力。
- Linux、MaixPy3 和 C SDK 开发路径。
- 标准底板配备摄像头、Wi-Fi 和 microSD 卡槽。

这些参数证明芯片具有相关能力，不证明当前板卡固件已经支持全部功能并行运行。目前尚未开展本项目的实机测试。

必须验证的核心问题：

1. 当前镜像是否能使用硬件编码器，输出可播放的 H.264 视频。
2. 摄像头是否支持编码与检测共享采集，或提供不同分辨率的输出。
3. 编码、模型推理、缓冲和网络传输同时运行时，64MB 内存是否足够。
4. 人员及火灾模型能否转换到 V831 的推理运行时。
5. 模型实际部署后的准确率、检测间隔和持续运行稳定性。

官方 MaixPy3 上手资料中的 MJPEG 图传属于调试能力，不能作为 H.264 服务可用的证据。目标检测示例中的部分 `person` 标签实际对应人脸模型，也不能直接作为完整人体检测模型使用。

## 3. 总体架构

```text
Maix-II Dock / V831
  摄像头采集
    ├─ 硬件 H.264 编码
    │    ├─ 短时滚动缓冲 → 事件录像
    │    └─ 手机观看期间 → 实时视频输出
    │
    └─ 缩放、抽帧 → NPU 检测 → 事件规则
                              ├─ 立即发送事件和截图
                              └─ 随后上传事件视频
                                       │
                                       ▼
树莓派
  轻量事件接收服务 + 事件数据库 + 文件存储
  视频接入与转发 + 远程访问 + 手机通知
                                       │
                                       ▼
手机
  实时观看 / 布防控制 / 报警查看 / 事件回溯
```

V831 持续采集、编码和检测。没有事件且无人观看时，不向树莓派持续上传视频，只发送少量状态信息。

手机观看时，树莓派接入 V831 的实时视频。事件发生时，V831 主动发送报警并上传相关片段。

树莓派不常驻解码、转码或推理。视频转发和事件文件封装尽量复用 V831 已生成的压缩数据。

## 4. V831 软件方案

### 4.1 开发路径

初期使用 MaixPy3 验证摄像头、网络和模型。

长期运行程序优先采用 C/C++ 与板卡 SDK，以便控制内存、使用硬件媒体接口、减少图像复制，并管理并行任务。不要求把 Python 调试程序直接扩展为最终监控服务。

验证前记录并冻结：

- 系统镜像来源、版本和校验值。
- SDK、编译工具链及依赖版本。
- 摄像头驱动和硬件编码示例。
- NPU 运行时、模型转换工具和模型文件版本。

选择有对应示例且可以复现的组合，不仅依据版本新旧选镜像。涉及刷机时，应先备份现有可用镜像和配置。

### 4.2 视频与检测并行

优先采用同一采集源的两条输出：

- 较高分辨率画面送硬件编码器。
- 低分辨率画面送 NPU。

如果 SDK 没有提供副路，验证是否能通过 SDK 缩放和抽帧获得检测输入，测量 CPU 与内存开销。

初始测试参数如下，均为候选值：

| 参数 | 起步值 |
| --- | --- |
| 编码格式 | H.264 |
| 视频分辨率 | 1280×720 |
| 视频帧率 | 15fps |
| 码率 | 1～2Mbps |
| 关键帧间隔 | 1～2 秒 |
| 检测输入尺寸 | 以兼容模型要求为准 |
| 检测频率 | 先测试每类任务每秒 2～5 次 |

编码后的数据供录像和实时服务复用，不为这两个用途重复编码。不在板端引入依赖软件转码的重型媒体处理流程。

使用有界队列。模型推理、文件上传或慢速观看客户端不得无限堆积数据、阻塞摄像头。实时播放落后时，可丢弃旧数据并从新的关键帧恢复。

### 4.3 人员入侵检测

首版手动切换“在家／离家布防”。

离家状态下：

1. 检测完整人体。
2. 判断目标是否进入配置区域。
3. 根据连续检测结果和持续时间确认事件。
4. 生成报警、截图和录像。
5. 合并同一持续事件，限制重复通知。

配置项包括区域、置信度阈值、确认时间和通知间隔。区域用于排除窗外、电视画面等与入侵无关的内容。

人脸身份识别作为后续能力，不作为首版入侵报警的必要条件。

### 4.4 疑似火灾检测

火灾检测持续开启，不受人员布防状态影响。

优先寻找兼容 V831 的轻量火焰、烟雾模型。火焰和烟雾分别评价，不能把其中一项的效果代表为另一项的效果。

模型部署路线：

1. 分别验证模型转换、推理和效果。
2. 测量两个模型同时驻留或轮换执行的内存与调度开销。
3. 如果分离模型负载过高，再评估联合检测模型。

不假设 NPU 可以同时执行多个模型，也不通过频繁加载模型来默认解决内存不足。

火灾检测不能依赖“画面有运动”才运行，否则可能漏掉缓慢出现的烟雾。人员检测与火灾检测应有明确的调度间隔，不能让其中一个任务长期占用推理资源。报警先发送事件和截图，不等待录像完成。

视觉检测结果表述为“疑似火灾”。其能力限于摄像头可见范围，真实烟雾、弱光和干扰场景需要独立验证；仅用显示屏播放火灾视频不足以完成验收。

未获得兼容模型、模型转换失败或效果不达标时，应记录为未实现或未通过验证，不把火灾检测列为已经具备的能力。

## 5. 事件录像与存储

### 5.1 保存策略

初始配置：

- 事件前缓冲：10 秒。
- 事件结束后补录：20 秒。
- 长事件：按约 60 秒分段，归属于同一事件。
- 相邻同类事件：按配置合并。

普通画面自动覆盖，不长期归档。事件视频保存在板端，上传成功后由树莓派归档。

如果内存不足，可采用 SD 卡短时环形片段。此时日常视频会暂时写入 SD 卡并持续覆盖，应明确区别于“不长期保存普通视频”，同时测量写入负担。

### 5.2 缓冲和可播放性

按码率 2Mbps 计算，10 秒压缩视频数据约为 2.5MB；实际内存占用还包含采集、编码、模型和队列。

录像从可解码的关键帧开始，保存必要的编码参数和时间戳。事前保留时长可能因关键帧边界略有增加。

板端优先保存 SDK 可稳定输出的短片段及清单。片段格式必须保留最终封装所需的编码配置与时间信息，不能仅保存无时间信息的裸数据并假设能够无损还原。

树莓派可以负责最终 MP4 封装，仅重封装压缩数据，不解码后重新编码。采用短片段和持久清单，避免故障造成整段长录像无法使用。

### 5.3 片段保护与容量管理

环形缓冲中的片段一旦被事件引用，应先完成保留标记或移入事件区，再允许环形缓冲继续覆盖。

正在写入、正在上传或被未完成事件引用的片段不能被清理。元数据使用原子更新，并预留空间记录故障和丢失事件。事件跨重启时保留已完成片段，将未正常结束的事件标记为中断。

配置独立配额：

- 普通滚动缓冲。
- 待上传事件。
- 已上传事件。
- 元数据及日志。

容量上限应根据实际 SD 卡、可用文件系统空间和期望断网时长确定。树莓派事件保留天数及总容量同样可配置。

达到容量上限时优先清理可删除的旧内容。未上传的疑似火灾事件优先保留；如果未上传事件仍占满空间，应执行明确的淘汰策略并记录丢失计数，不能无限增长。

SD 卡故障时，检测和即时报警应尽可能继续运行，同时报告“录像不可用”。

## 6. 树莓派及手机访问

树莓派部署以下组件：

| 组件 | 用途 |
| --- | --- |
| 轻量事件服务 | 接收事件、截图、片段和设备状态 |
| SQLite | 保存事件索引、配置及上传状态 |
| 文件存储 | 保存事件录像和截图 |
| go2rtc，候选 | 接入压缩视频，提供浏览器观看入口 |
| Tailscale，候选 | 手机与树莓派建立私有远程连接 |
| 简单手机网页 | 实时观看、事件列表、回放和布防 |

事件服务可采用 Python 等易维护的技术栈。上传必须流式写入，不能把完整录像读入内存。

建议树莓派使用网线连接路由器。服务设置资源上限，验证其与树莓派已有任务共存时的负载，不独占设备。

### 6.1 实时视频链路

首选验证路径：

**V831 硬件 H.264 输出 → 轻量 RTSP 服务 → 树莓派 go2rtc → 手机播放。**

RTSP 服务需验证在板卡工具链上的兼容性和资源占用，不把它视为现有固件必带功能。若 SDK 自带其他可用压缩流协议，可比较接入成本后选择；必须记录最终采用的协议和实现。

编码器重启或参数变化后，服务更新编码参数，并从关键帧恢复播放。

事件消息优先发送，事件录像上传采用限速队列，避免占满带宽影响通知和实时观看。实时观看客户端断开后，树莓派应释放上游视频连接，验证所选组件的按需接入配置。

### 6.2 外网观看

手机与树莓派使用 Tailscale 建立可达连接。

网页能打开不代表视频连接一定能建立，还要验证 WebRTC 的媒体地址和端口能否到达。必要时尝试受支持的 TCP 播放路径或 HLS 重封装方案。播放格式须与目标手机浏览器兼容，不能默认任何 H.264 编码配置都能直接播放。

实际检查：

- 手机使用移动网络能否观看。
- 是否经过中转。
- 首帧时间、播放延迟及持续稳定性。
- 页面、实时媒体、事件回放是否都可达。

远程访问需要身份验证。V831 服务主要面向家庭局域网，不依赖直接暴露到公网。事件上传接口验证设备身份。

### 6.3 手机通知

通知模块使用可替换接口，首版选一个手机可接收的渠道，先完成文本、截图及事件链接通知。

尚未确定具体通知渠道，这不阻塞设备验证，但应在报警闭环阶段完成选择，并实测手机端收到通知的时间。树莓派收到事件与手机收到通知分别计时。

## 7. 事件通信与异常恢复

### 7.1 上传顺序

1. 立即发送事件信息和截图。
2. 事件持续期间更新状态。
3. 完成片段后上传视频。
4. 树莓派确认持久保存后，V831 再将其标记为可清理。

事件使用唯一 ID，支持重复上传和幂等处理。片段使用序号与校验值，断网重连后只补传未确认内容。上传重试采用有上限的退避，不能在网络故障时持续占用 CPU。

事件信息至少包含：

- 设备 ID、事件 ID、事件类型。
- 开始和结束时间、时间可信状态。
- 模型版本、配置版本和布防状态。
- 检测结果及截图。
- 视频片段列表和上传状态。

### 7.2 布防与时间

树莓派下发布防配置，V831 确认实际应用后，手机才显示已生效。断网时继续执行最后一次确认的配置。

首次部署必须明确选择布防状态，不把未初始化状态显示为已布防。配置在板端持久保存，重启后恢复最后确认的状态；火灾检测始终开启。

设备时间从树莓派或时间服务同步。无法获得可信时间时，用启动标识、单调时钟及事件时长保存记录，不伪装为准确日期时间。系统时间校正不能改变用于判断持续时间的单调时钟。

### 7.3 故障检测

分别监测：

- 最近一次成功采集。
- 最近一次编码输出。
- 最近一次人员检测完成。
- 最近一次火灾检测完成。
- 存储和上传状态。

进程仍在运行但某个环节停滞时，也应报告故障并恢复。恢复顺序为模块重建、进程重启，再视支持情况使用看门狗；限制连续重启，保留原因。各阶段超时以实测正常最大耗时设置，并记录配置。

树莓派区分“设备失联”“视频故障”“检测失效”和“录像失败”，避免只显示在线状态。树莓派自身不可用时，板端继续本地检测和录像，但手机通知及远程观看可能不可用；手机界面不得把过期状态视为当前正常状态。

## 8. 实机验证与验收

### 8.1 验证阶段

| 阶段 | 验证内容 | 通过条件 |
| --- | --- | --- |
| A：板卡与固件 | 镜像、SDK、采集、硬件编码、兼容模型 | 可复现构建；连续编码 1 小时；生成的视频可播放 |
| B：并行能力 | 编码加人员检测，再加入火灾检测 | 无内存耗尽；检测任务没有长期饥饿；记录各类检测最大间隔 |
| C：事件链路 | 事前缓冲、补录、上传、重传、空间清理 | 事件片段完整可播放；重复上传不产生重复事件 |
| D：手机访问 | 家庭 Wi-Fi、移动网络、布防及回放 | 可观看和回溯；布防状态准确确认 |
| E：长期运行 | 全负载、断网、存储故障及恢复 | 连续运行 24 小时，无无法解释的卡死、内存耗尽或反复重启 |

A 阶段还应验证至少一个模型的转换和加载路径。B 阶段的模型必须在量化后、实际板端运行条件下测试，不能使用训练环境结果替代。

C 阶段加入环形覆盖与事件保留竞争、长事件分段、写盘失败、满盘、进程中断后的恢复测试。D 阶段叠加事件上传，验证视频观看不会使检测停滞。

### 8.2 初始验收目标

以下用于指导测试，不代表已有性能：

- 人员检测：在实际安装位置进行至少 20 次入侵测试，至少 19 次成功触发，并记录照明、距离和遮挡条件。
- 检测调度：起步目标为每类任务正常运行时最长完成间隔不超过 1 秒，超出时报告性能不达标。
- 报警传输：网络正常时，板端确认事件后 2 秒内树莓派收到事件信息。
- 手机观看：正常网络下首帧约 5 秒以内，延迟约 3 秒以内。
- 断网恢复：断网 10 分钟期间继续检测和保存事件，恢复后补传。
- 火灾模型：先在有标注测试集上评价量化后的模型，再测试真实机位干扰；火焰召回率暂以 90% 为优化目标，实际机位负例测试暂以每 24 小时不超过 1 次误报为目标。

火灾测试必须记录样本数量和条件。烟雾识别单独验收，未达标时明确标注尚不支持。测试包括蒸汽、反光、电视画面及不同照明；人员检测也覆盖弱光和遮挡。测试样本与训练样本应分离，采集过程不制造危险火情。

上述指标不能用于宣称安全认证或保证所有火情都能发现。手机通知端到端时延在通知渠道确定后单独测量。

## 9. 资源不足时的处理

按以下顺序优化：

1. 停止不必要的屏幕刷新、IDE 服务和调试输出。
2. 减少图像复制，缩短有界队列。
3. 限制后台上传带宽和实时观看负载，必要时暂停实时观看。
4. 降低编码分辨率、帧率和码率。
5. 优化模型规模、检测输入尺寸及调度方式。

必须同时记录系统空闲内存、进程占用和媒体硬件保留内存，不能仅依据进程内存判断资源是否足够。根据 SDK 实际预留方式制定最低内存余量，覆盖事件触发、录像上传和手机观看时的瞬时分配，并在 B 阶段固化其数值。

检测与异常报告优先于额外观看和后台上传。存储和网络路径不得阻塞检测。降低检测频率后如果超过约定的最大完成间隔，应报告不达标，不默默降低保障能力。

如果最低可接受的视频配置下，编码与所需检测仍不能稳定并行，就判定当前固件或板卡组合未达到要求。优先尝试其他可复现的 SDK 路径；仍失败则给出测量结果和具体能力边界，再讨论取舍，不默认把识别移到树莓派。

## 10. 推进顺序与交付物

先完成固件和硬件能力验证，再进入完整应用开发：

1. 确认 V831 系统、SDK、编码接口和模型转换链。
2. 跑通硬件编码、树莓派接入及手机远程观看。
3. 在 V831 上加入人员检测，形成事件报警和回溯闭环。
4. 加入火焰及烟雾候选模型，验证并行能力和实际效果。
5. 完成容量管理、故障恢复和长期运行测试。

每一阶段交付配置、复现步骤和测量结果，明确区分：

- 已验证能力。
- 已实现但仍有限制的能力。
- 未通过验证的能力。

最终文档应包含系统架构、固件版本清单、部署步骤、配置说明、测试结果和已知限制。

## 11. 进入验证阶段时需记录的现场信息

这些信息由设备检查获取，不阻塞设计方案落地：

- V831 当前镜像、SDK 和启动服务，摄像头及 Wi-Fi 状态。
- SD 卡容量、可用空间、文件系统与现有数据。
- 树莓派系统版本、现有服务和基线资源占用。
- 摄像头安装位置、检测区域与昼夜照明。
- 目标手机系统、远程网络连接情况和通知渠道。
